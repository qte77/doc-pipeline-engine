## What V1 actually produces (vs V2)

Concrete content delta on the invoice sample:

- **V2** (one bullet): `Standard Form 1034 VOUCHER NO.`
- **V1** (~1,700 chars, structured): Overview / Identification Fields /
  Itemization Table / Payment Section / Certification / Signing Rules /
  Legal Basis / Key Entities. Names the issuer (U.S. Treasury), cites
  authorities (31 U.S.C. §82b/82c, TFRM 4-2000), enumerates form
  identifiers (1034-119, NSN 7540-00-900-2234).

This is the A/B value the prototype was built for: V1 produces
semantically structured summaries with real entities + claims; V2's
single-leaf `v2_normalize` shortcut produces 1 trivial claim per doc
regardless of input size (tracked in
[#33](https://github.com/qte77/doc-pipeline-engine/issues/33)).

## Faithfulness gaps and surprises

1. **V1 honestly reports empty input.** The diagram JPG OCRed to zero
   chars (Tesseract found no readable text on the board photo). V1's
   summary opens with `"The source document … contains no substantive
   content"` and emits 1 degenerate claim — schema-valid and
   semantically truthful. No hallucinated content.

2. **V1 wall-time scales roughly with input size.** Contract (220K
   chars) took 388s; invoice (5K chars) took 80s. Most of that is
   model latency on `claude --print` round-trips (4 calls per sample:
   normalize → analyze → render → eval). Each call carries the input
   text as the user prompt; cache reuse across stages keeps cost
   bounded but doesn't reduce per-call latency much.

3. **`Argument list too long` was a real bug.** Initial implementation
   passed the user prompt as a positional argv, which hit `E2BIG` on
   the 220K-char contract. Fix: switch to stdin (`subprocess.run(...,
   input=user)`). Caught only because we ran the contract sample —
   short prompts mask the bug. Now stdin-only for the user prompt;
   system prompt stays as a flag (always short).

4. **Cost-axis honesty caveat.** The `claude --print` JSON envelope
   reports `total_cost_usd` and per-call `usage` (input/output/cache
   tokens), but `_v1_client` does not yet stamp those into the
   `EvalReport`. So the `latency_ratio_v1_over_v2` axis is real
   wall-time but the cost axis isn't computed yet. Backend-marker
   follow-up tracked separately.

5. **V2 is structurally unchanged from run 1.** V2 wall-times,
   markdown sizes, and claim counts match run 1 ± noise (~10%). The V1
   leg is the only new signal in run 2.

## Open follow-ups (still standing after this run)

- **Backend marker in `EvalReport`** — record which V1 backend (SDK vs
  CLI) served each call, plus `total_cost_usd` from the CLI envelope.
  Required before the cost axis is comparable across backends.
- **V2 normalize: heading-tree reconstruction** — still 1 claim per
  doc, tracked in
  [#33](https://github.com/qte77/doc-pipeline-engine/issues/33).
  Without it, the V2 summary is mostly trivial regardless of input.
- **Full `--extra v2` (spaCy NER)** — still skipped because the
  codespace is on Python 3.14. Switching to 3.13 (planned in the new
  devcontainer) will populate V2 entities.
- **Claude CLI 1M-token cache reuse** — the envelope shows huge
  `cache_creation_input_tokens` on first call and `cache_read_input_tokens`
  on subsequent ones. Worth measuring whether running stages back-to-back
  benefits more than running them in isolation.
